**对你下一轮 PheroOS 研究，我建议引入一个能力经过校准的外部大模型 API，而不是继续只使用目前的本地 1.5B／3B 模型。**它最有价值的作用，是帮助你区分：**失败来自模型能力、动作接口，还是群体协调机制。**

但要把两件事分开：

> **“更强的模型可能更适合当前诊断”，不等于“API 部署方式天然优于本地部署”。**

目前还没有在你的新实验环境中完成这项直接比较，因此不能保证换成 API 就提高成功率。我的建议也不是全部迁移，而是：**本地保留，增加强 API 对照，之后再研究混合调度。**

## 一、为什么你现在值得引入强模型 API？

你的 R4 replication 使用了 **3,402,842 tokens**，其中公共检查器拒绝的动作消耗 **2,970,028 tokens，约占 87.28%**；同时，没有一个证据任务 episode 收集齐全部三个最终版本来源。这里的拒绝不全是格式错误，也包括动作目标、证据和语义检查失败。

这使当前实验存在一个关键困难：

> **当 agent 连基本动作选择和证据获取都经常失败时，很难判断一种协调机制本来有没有价值。**

例如，同样是“多个 agent 没有完成证据任务”，原因可能完全不同：

| 可能原因            | 强模型 API 能帮助判断什么？      |
| --------------- | --------------------- |
| 模型无法稳定理解动作与参数   | 经校准的 API 模型能否显著减少这类失败 |
| 给齐证据后仍不能整合答案    | 是否存在明显的模型能力瓶颈         |
| 模型会回答，但总在重复检查   | 是否需要修改任务规划与工作复用       |
| 系统根本没有把必要证据交给模型 | 换模型仍不能替代证据索引与获取机制     |
| N 改变后输入和行为完全相同  | 换模型不能把“重命名轮次”变成真正协作   |

**所以，API 的首要价值不是让结果更好看，而是提高诊断的区分能力。**

如果强模型在同一接口、同一信息边界下仍卡在同一个地方，你就更有理由检查系统设计；如果它明显改善，则说明之前的结果混入了较强的单体能力限制。两种结果都对你有价值。

## 二、这是否违背“弱个体通过群体组织完成目标”的愿景？

**不违背，但必须分阶段验证。**

你现在同时在试图回答两个问题：

> **问题 A：这套交互机制有没有用？**
> **问题 B：它能不能让更弱的模型达到有用的系统表现？**

不应一开始就把它们绑在一起。否则，只要弱模型无法执行基础动作，两个问题都会得到失败结果，却不知道具体失败在哪里。

我更建议采用：

**先用具备足够动作能力的模型验证交互闭环，再逐步降低模型能力、上下文和预算，找出机制仍然有效的边界。**

不过也要避免相反的问题：如果一个强模型单独就能轻松解决所有测试，群体策略也可能没有改善空间。这时可以研究重复工作、成本、故障恢复或有真实信息互补的任务，而不是故意限制对照，让群体看起来更强。

另外，**用强 API 模型配上有限上下文和局部信息，可以研究“受限信息下的协作”，但不能据此宣称实现了“低算力弱模型的群体优势”。**限制可见信息和降低模型本身能力，是不同的实验变量。

## 三、本地与 API 应该分别承担什么？

我建议这样分工，而不是二选一：

| 任务                    | 建议环境          | 目的                |
| --------------------- | ------------- | ----------------- |
| 协议、账本、取消、租约和确定性测试     | 本地 mock／确定性工具 | 不需要为工程回归支付模型费用    |
| 当前本地模型的错误诊断           | 本地模型          | 保留已知基线和错误模式       |
| 动作可用性、证据整合能力对照        | 强 API 模型      | 判断是否被单体能力限制       |
| 2–4 agent 的真实协作 pilot | 本地与 API 分别运行  | 检查机制是否依赖某个模型水平    |
| 低成本 worker＋按需升级       | 后续混合实验        | 验证升级是否值得，而不是预设它有效 |

**我不建议第一步就采用“本地弱 worker＋一个强 API 总指挥”。**

因为你上一轮已经出现过归因困难：Mixed 的首次成功都出现在较大模型槽位，但这无法独立确定前面小模型工作的贡献。

如果现在直接把强 API 放到最后兜底，很容易再次得到：

> 系统完成了，但不知道是群体协作有效，还是强模型最后单独解决了问题。

先做清楚的能力对照，比直接做复杂混合架构更有用。

## 四、下一轮怎么比较，才不会把“模型升级”误算成“PheroOS 优势”？

### 第一步：小规模能力诊断

可以先选 **20–40 个开发用任务实例**作为初始诊断规模；这是建议的试运行规模，不是统计功效保证，也不应全部只是旧四个任务换参数。

本地与 API 都运行之前 Goal 中的三种条件：

**给齐证据并要求提交；给齐证据但允许自由行动；完全自主获取证据。**

重点看失败发生在哪一层，而不是只看总成功率。尤其要保留格式、非法目标、缺少证据、重复检查、提交失败和最终答案错误的分类。

模型选择应根据这批独立诊断任务的表现确定，而不是根据厂商标签默认它已经是“强模型对照”。

### 第二步：在同一个模型内部比较协调策略

核心比较应该是：

| 模型后端      | 强简单 blackboard | PheroOS 候选机制 |
| --------- | -------------- | ------------ |
| 当前本地模型    | A              | B            |
| 选定 API 模型 | C              | D            |

真正回答协调问题的是：

$$
\Delta_{\text{local}}=Q(B)-Q(A)
$$

$$
\Delta_{\text{API}}=Q(D)-Q(C)
$$

而不是用 **API＋PheroOS** 去对比 **本地小模型＋简单策略**，然后把全部提升归因于 PheroOS。

每个模型内部，要统一工具、任务、动作接口、可见信息和预算规则。跨模型比较则另报质量、实际用量和成本，不要假定不同 tokenizer 的“相同 token 数”代表完全相同的计算资源。

### 第三步：再研究混合调度

只有前两步清楚后，才比较：

> 本地独立完成、API 独立完成、本地＋按公开条件升级。

升级应由可观察的停滞、反复失败或证据冲突触发，不能看隐藏答案决定。也不能把 API 模型的自我判断当成最终真值；已有可执行测试和独立任务检查器应继续保留。

## 五、API 能改善动作格式，但不能代替正确性与权限检查

以 OpenAI API 为例，支持的模型和请求配置可以通过 strict function calling／Structured Outputs 约束参数符合声明的 JSON Schema。这适合你的动作接口，例如把 `target` 限定在当前公开合法来源中，而不是让模型复制 `index_entry` 占位符。([OpenAI Help Center][1])

但官方文档也明确指出，**符合 schema 的输出仍然可能在内容上出错**。字段合法，不代表选对了来源、推理正确或具备执行权限。([OpenAI Developers][2])

因此，应继续保留：

```text
模型提出动作
→ 参数与目标检查
→ 当前权限检查
→ 工具执行
→ 回执与证据验证
→ 最终任务评估
```

并且，结构化接口应成为所有比较方法共同使用的基础设施。不能只给候选策略提供严格工具调用，却让对照继续使用容易出错的自由文本。

## 六、对现有 runtime，接 API 不只是加一个 Key

你的 `SessionDriver` 已经有可替换的 `ModelAdapter`，这是好基础；但当前生成路径先调用 `count_tokens()`，按输入量和最大输出预留资源，再执行生成并接收回执。现有 `LocalModelAdapter` 则依赖本地模型文件和 tokenizer。

所以我建议新增独立的 **RemoteModelAdapter**，不要把远程请求塞进 `LocalModelAdapter`。接入时有三个特别重要的问题。

### 1. 预估用量与实际计费用量分开

远程请求的调用前计数，应使用该供应商支持的可靠方法或明确的保守上界；调用后保留原始 usage 回执，不能伪造 token 数来满足旧的本地契约。

对推理模型，还必须考虑不可见的 reasoning tokens。以 OpenAI 为例，它们按输出 tokens 计费，并受相应输出上限约束；设置过小上限可能在生成可见答案前就耗尽预算。**不能机械沿用本地实验的 256 输出 token 设置，再把没有答案解释成模型失败。**([OpenAI Developers][3])

如果这需要修改账本的计量语义，应使用新的实验性 profile／版本，保留旧数据的含义。

### 2. 不能让 SDK 的隐式重试破坏账本

OpenAI 官方 Python SDK 默认会对部分连接错误、限流和服务器错误自动重试两次。对于你强调“一次 dispatch 对应可追踪账目”的系统，这种默认行为需要显式处理。([GitHub][4])

我的建议是：**先关闭隐藏重试，由 runtime 记录和管理每次尝试。**回执丢失时保持 `unknown`，不能当成零成本，也不能为了完成任务自动重发。

### 3. API 回放与重新生成不是同一件事

保存原始请求和响应，可以重放既有执行记录；重新调用远程模型，不应被假定会逐字复现。即便某些接口支持 seed，官方也说明确定性并非保证。([OpenAI Developers][5])

因此要保存模型版本、接口、参数、请求 ID、完整 usage，以及可获得的服务端版本信息；API 实验的延迟还应与本地 GPU 性能实验分开解释。

## 七、费用与权限：应该怎么改上一轮 Goal？

上一轮 Goal 的“禁止付费 API”是为了防止 Codex 自行花钱，**不是说明本地模型在科研上一定更好**。

我建议将下一轮执行策略调整为：

> **默认仍运行本地与无模型测试；只有明确指定 API 供应商、模型、总费用上限、请求上限和允许的数据范围后，才启用远程能力诊断。完成诊断后，再决定是否运行有限协作 pilot。**

**API Key 存在，不等于允许无限调用。**也不要只依赖服务商页面上的预算提醒。以 OpenAI 为例，项目月预算是软阈值，超过后请求仍可能继续，应用层需要自己的调用前预算控制。([OpenAI Help Center][6])

这里也要分清：**Codex 帮你开发代码，与 PheroOS 通过 API 运行实验，是两套使用路径。**ChatGPT 订阅与 OpenAI API 计费分开，不能把订阅当作实验的免费 token 池。([OpenAI Help Center][7])

---

## 我的最终建议

**引入强 API，值得；立即全面替换本地模型，不值得。**

下一轮最合理的顺序是：

> **本地完成接口和证据机制修复 → 强 API 做小规模能力诊断 → 同模型内比较简单策略与 PheroOS → 再研究低成本 worker 与按需升级。**

你现在需要的不是更多低质量调用，也不是让强模型把所有错误兜住，而是一个可信的能力对照，帮助判断：

> **当 agent 已经能够正确执行基本工作时，PheroOS 的组织方式是否真的让它们做得更好。**
